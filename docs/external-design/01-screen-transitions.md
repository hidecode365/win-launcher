## モーダル・ダイアログのキー操作原則

モーダル・ダイアログにおけるキャンセル（Escape）と確定（Enter）は、**意図的に非対称に扱う**。

- **キャンセル（Escape）は、DOM 上のフォーカス位置に依存させない。** `App.tsx` の window レベル共通 `keydown` リスナーで処理し、フォーカスがどこにあっても常に効くようにする
- **確定（Enter）は、ブラウザ標準のフォーカス経路に委ねる。** Tab でフォーカスを移動し、フォーカスされたボタン上で Enter を押すと `click` が発火する、というブラウザ既定の挙動をそのまま使う。**window レベルリスナーに独自の Enter 分岐を設けない**

この非対称性は、キャンセルと確定で「誤爆したときの被害の非対称性」が根本的に異なることに基づく。キャンセルは誤爆しても失われるのは操作の途中状態だけだが、確定は破壊的操作（シャットダウン・削除等）を引き起こしうる。したがってキャンセルは「確実に効くこと」を優先し、確定は「意図しない経路では効かないこと」を優先する。

<a id="modal-key-policy-history"></a>

### この原則に至った経緯

従来の原則は「モーダルのキー操作はフォーカス位置に依存させず window レベルへ一本化する」であり、Escape と Enter を区別していなかった。しかし以下の経緯により、確定（Enter）については一本化の対象から外す方針へ改めた。

- **原則が生まれた経緯の不具合は、いずれも Escape（キャンセル）が効かない事象であり、Enter（確定）ではなかった。** 登録ダイアログを★ボタンから開いた直後に Escape が効かない、システムコマンド確認モーダルでキャンセルできない、といった症状が発端であり、「Enter も window レベルへ寄せる」という部分は当時の対応で機械的に併せて行われたものだった
- **`systemCommand` は window レベルリスナーに独自の Enter 分岐を持っていた。** そのため、キーのチャタリング／WebView2 の入力二重発火（3ms 間隔での 2 回の `keydown`）により、確認ダイアログが開いた直後に即座に確定され、**破壊的操作が確認を経ずに実行される事故**が発生した
- **一方 `deleteFolder`（フォルダ削除確認）は独自の Enter 分岐を持たず、ブラウザ標準経路のみだったため、同種の事故が発生していない。** 同じ「確認モーダル」でありながら片方だけが事故を起こしたことが、独自 Enter 分岐そのものが原因であることを示している

<a id="system-command-enter-removal"></a>

### `systemCommand` の是正方針（実装は別途）

上記を踏まえ、`systemCommand` については以下をいずれも**削除**し、`deleteFolder` と同じブラウザ標準経路に統一する。

- window レベルリスナーの独自 Enter 分岐
- 暫定対処として導入した 300ms の猶予期間（`SYSTEM_COMMAND_CONFIRM_GRACE_MS`）

猶予期間は「二重発火の 2 回目を時間で弾く」という対症療法であり、原因（独自 Enter 分岐の存在）そのものを取り除けば不要になる。

**この是正の実装は、設計書整備の完了後に優先度高で着手する**（本書作成時点では未着手であり、コードには独自 Enter 分岐と猶予期間の両方が残っている）。

## 第3の分類「fullscreen overlay」を認めた理由

表2の `ocrPreview` の種別は、view でも modal でもない第3の分類 **fullscreen overlay** として確定した（PO 決定）。

**fullscreen overlay の定義**：**画面の中身をまるごと覆うが、下位の view の状態・ロジックは動き続けるもの。** 現時点の該当は `ocrPreview` のみ。

view・modal のどちらかに寄せず第3の分類を新設したのは、どちらに寄せても歪みが出るためである。

- **view として `MainView` 型へ統合すると**、「view が切り替わっているのに検索ロジックは動き続ける」という現状の挙動と噛み合わない（`ocrPreview` 表示中もクエリの入力・検索の実行・内部 state の更新はすべて通常どおり継続する）
- **modal と呼ぶと**、「全画面を覆う modal」という他に例のない例外分類を認めることになる（他の modal はいずれも元の画面の上に重なるだけで、下位の画面要素を隠しきらない）

どちらに寄せても実態と食い違う説明が残るため、**実態どおり「view でも modal でもない第3のもの」として名前を与える方が、後から読む人の混乱が少ない**と判断した。

**新しい状態を追加する際の判断基準**：画面の中身をまるごと覆うかどうか（覆わないなら modal）、および下位の view の状態・ロジックが動き続けるかどうか（止まるなら view）の2軸で分類する。両方に該当する場合のみ fullscreen overlay とする。
