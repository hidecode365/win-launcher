## 表3: 一覧データ構造定義（3層構造）

本アプリの一覧は「元データがどういう形をしているか」と「選択（↑↓・Enter）がどの配列の上で解決されるか」が**別の層**になっている。両者を混同すると「木構造の一覧は選択の仕組みが違うはずだ」という誤解を生むため、以下の 3 層として定義する。

| 層 | 定義 | 現状の該当 |
| --- | --- | --- |
| **元データ構造（木）** | 親子関係を持つ木構造。選択に乗る前に平坦化される | お気に入り、（将来）メモ |
| **元データ構造（フラット）** | 順序付きフラット配列 | 検索結果、クリップボード履歴 |
| **選択レイヤー** | `{key: string}[]` を満たす平坦配列。木構造はここへ平坦化してから乗る | 通常モード（`ResultRow[]`）／`clipboardMode`（`SelectableItem[]`）／`favoriteMode`（`FavoriteTreeRow[]`）／お気に入り編集ビュー（`FavoriteEditTreeRow[]`） |

**重要な帰結**：木構造かフラット構造かは**選択の仕組みには影響しない**。木構造（お気に入り）も平坦化済み配列（`FavoriteTreeRow[]`。各行が `depth` を持つ）として選択レイヤーに乗るため、フラット構造の一覧とまったく同じ選択実装を共有する。

### 補足事項

- **「最近使ったファイル」は独立した選択ドメインではない。** `/recent` モード中の一覧は `results` へ流し込まれ、`ResultRow[]`（`kind: "file"` の行）に吸収されている。したがって選択レイヤーとしては通常モードと同一であり、独立した構造型として数える必要はない
- **クリップボード履歴の選択レイヤーは `{key: string}` のみの最小構造。** 実体（`ClipboardEntry`）は `useClipboard.ts` 側にあり、選択レイヤーには識別子だけが渡る。これは `useSearch` が `useClipboard` の戻り値に依存できない（依存すると循環になる）ための**逆方向 push 設計**によるもので、意図的な構造である
- **`prefixCommandMode` と `pathPasteWizardMode` は選択レイヤーに乗っていない。** これらは生インデックス書き込み（`setSelectedRaw`）のままであり、**意図的に維持している**（非同期の書き込み競合を追加する具体的な予定が無いため）。将来これらに非同期のデータ差し替えが入る場合は、選択レイヤーへの移行を検討する

### 新しい構造型を追加する場合

**上記 3 層以外の構造型（例：グラフ構造、複数の選択カーソルを同時に持つ一覧など）を追加する場合は、CC の判断では行わず PO 承認を要する。**

補足：この制約は TypeScript の型システムでは強制できない。選択レイヤーの契約は `{key: string}` という構造的部分型のみであり、この形を満たす任意の新しい型がコンパイルエラーなく渡せてしまう。したがって本ルールはドキュメント上の合意として運用し、200_設計 工程でのレビューによって担保する。

<a id="selection-model"></a>

## 選択モデル（intent 方式）

**選択（`selected`）は、行番号や画面上の位置ではなく、「ユーザーが選びたい対象の識別子」（intent）から毎回導出する値として扱う。書き込み可能な state にしない。**

この原則は以下を意味する。

- 選択の実体は「今どの行が選ばれているか」という**位置情報ではなく**、「ユーザーはどの対象を選びたいのか」という**意図（識別子）**である
- 一覧が非同期に差し替わった場合（検索結果の到着・フォーカス復帰時の再取得・ピン止めの追加/解除等）でも、同じ識別子が新しい一覧に存在する限り選択は維持される
- 識別子が新しい一覧に見つからない場合、「見つからない」は「先頭へリセットする理由」ではなく「まだ一覧に反映されていないだけ」として扱い、見つかるか一定時間が経過するまで現在の表示を維持する
- 選択に相当する新しい値を設計する場合も、同じく「意図」と「現在の候補一覧」から導出する形を優先し、直接 state 化しない

**この原則を採用した理由**：選択が複数の非同期処理からそれぞれ書き込める state だった頃、ピン止め操作・ドラッグ&ドロップ・検索結果の解決がそれぞれ独立に選択へ書き込む経路を持ち、「一瞬正しい行が選ばれた直後に先頭へ戻る」という不具合が繰り返し発生した。個別の抑止フラグで特定の書き込みだけを止めても書き込み経路自体は残り続けるため、別のタイミングの組み合わせで同種の競合が再発する。書き込み経路を 1 本に絞る（＝導出値にする）ことで、この構造的な問題そのものを解消した。

**適用範囲**：[表3](#list-structure-layers) の「選択レイヤー」に挙げた 4 ドメインすべて。`prefixCommandMode`／`pathPasteWizardMode` は前述のとおり適用対象外（意図的）。

> 実装の詳細（`SelectIntent` 型・`resolveSelected()` の実装・リセットトリガーの一本化・ホバー抑制・非同期復元とタイムアウト等）は [docs/internal-design/result-list-and-selection.md](../internal-design/result-list-and-selection.md) を参照する。本書には原則のみを置き、実装詳細を重複して書かない。

<a id="selection-timeout-limitation"></a>

### 既知の制約：待ち時間の上限が壁時計依存であること

上記の「見つかるか一定時間が経過するまで維持する」の**一定時間は現在1秒の固定値**（`SELECT_INTENT_TIMEOUT_MS`）であり、壁時計で計測している。これに起因する既知の制約を記録する。

**症状**：検索フォルダが巨大でファイル検索の応答が1秒を超える環境では、**アプリが正常に動作しているにもかかわらず選択が先頭へ飛ぶ**。ユーザーには「たまに選択が飛ぶ」という再現性の低い不具合として体験される。

**原因**：本来諦めるべき条件は「その対象を生むはずだった非同期取得が完了し、それでも見つからなかった時」であるのに対し、現在は「1秒経った時」で代用している。応答時間はマシン性能・フォルダ規模・ディスク速度に依存するため、**開発機では再現せずユーザー環境でのみ発現する**。

**改善余地**：既存の世代ID管理（非同期呼び出しが最新かを判定する仕組み）が「どの取得がいつ完了したか」の情報を既に持っているため、壁時計ではなくこの完了シグナルを見て諦める設計に変更できる。ただし複数の非同期処理が絡む操作（ピン止め追加など、保存と再取得の両方が走るもの）では「どの完了を待つか」を意図側に持たせる設計変更が必要になる。またIPCがハングした場合の最後の砦として、壁時計のタイムアウト自体は（現在より大幅に長い値で）残すのが妥当。

**優先度：低**（`systemCommand` の[是正](01-screen-transitions.md#system-command-enter-removal)より低い）。あちらは破壊的操作の誤実行という実害が既に発生しているのに対し、こちらの症状は「選択が先頭に戻る」に留まるため。着手する場合は 200_設計 の独立したトピックとして扱う。

**この制約は対症療法ではない**：時間で判別しているのは「まだ届いていないだけか／永遠に来ないか」という本質的に不確定な事象であり、対象が二度と現れないケース（ファイルが削除済み等）は実在するため、諦める規則自体は必ず必要である。原因を取り除けば不要になる類のもの（`SYSTEM_COMMAND_CONFIRM_GRACE_MS` のような、欠陥を隠すための時間ガード）とは性質が異なる。
