## ピン止め・お気に入り・メモの共通データ構造（`FavoriteNode`）

ピン止め・お気に入り・メモの3機能を、単一の型 `FavoriteNode` で管理する。フィールドは `{ id, parentId, type, name, value, order, collapsed }`（`collapsed` はフォルダの開閉状態を表す真偽値。デフォルト `false`。詳細は REQUIREMENTS.md「フォルダの開閉状態（`collapsed`）の永続化と絞り込みとの関係」節を参照）。

**`children` を持つ入れ子構造ではなく、`parentId` を持つフラットな配列（隣接リスト方式）を採用する。**

採用理由：既存の `FolderEntry` と同じく `Vec<T>`／配列としてそのまま扱えるため、Rust 側に再帰的な型定義（`Box<FavoriteNode>` を含む木構造）を導入する必要がない。ツリー表示・ドラッグ&ドロップによる階層移動も、ノードの `parentId` を書き換えるだけで「別の親へ移動」を表現できる（再帰構造だと、移動のたびに元の親の `children` から取り除いて新しい親の `children` へ挿入するというツリー操作が必要になるのに対し、フラット配列なら1フィールドの更新で済む）。

**永続化方式**：`settings.json` の `"favorites"` キーに `Vec<FavoriteNode>` をそのまま保存する。読み書きは既存の `folders`/`appSettings` と同じく **Rust コマンド経由**とし、frecency・clipboardHistory のようなフロントエンドから JS の plugin-store API で直接読み書きする方式は**採用しない**（将来 `clipboard`/`command` 型のフィールドを追加する際、Rust 側の型定義に `#[serde(default)]` を付与するだけで後方互換を保証できるようにするため）。

**保存方式は2案を比較して機能ごとに使い分けている。**

| | 案A：全量置き換え方式 | 案B：個別コマンド方式 |
| --- | --- | --- |
| 呼び出し方法 | 更新後の配列全体を組み立てて `set_favorites` へ渡す | `add_favorite`／`remove_favorite`／`rename_favorite_node`／`move_favorite_node_to` 等、1操作＝1コマンド |
| フロント側の負担 | 呼び出し前に配列全体を組み立て直す必要がある | 対象ノードのIDと変更内容だけを渡せばよい |
| 書き込み頻度との相性 | 低頻度な操作（追加・解除・並び替えのみ）に向く | 1件ずつ都度確定させたい操作が多いUIに向く |

採用結果：ピン止め（`PINNED_FOLDER_ID` 直下の追加・解除・並び替え）は**案A**（`set_favorites`）、お気に入りツリーの編集操作（`add_favorite`／`add_favorite_folder`／`rename_favorite_node`／`remove_favorite`／`remove_favorite_folder`／`move_favorite_node_to`／`set_favorite_folder_collapsed`）は**案B**を採用した（REQUIREMENTS.md「お気に入り編集ビュー」節の「1操作＝1即時Rustコマンド呼び出し」方式と同じ）。

**採用理由の明文化状況**：機能によって異なる方式を採った理由そのものは、コミット履歴・REQUIREMENTS.md・`docs/internal-design/favorites-data-model.md` のいずれにも明記されていない。REQUIREMENTS.mdは「既存の `/favorite` 暫定UI（段階2で前倒し実装した上下移動・削除）と同じ方式を踏襲する」と既存パターンへの追従を述べるのみで、案Aではなく案Bを選んだ根拠自体の記載はない。

## 予約フォルダ（固定ID）

ルート直下の「ピン止め」「お気に入り」「メモ」の3ノードは、`PINNED_FOLDER_ID`（`"__pinned__"`）／`FAVORITES_FOLDER_ID`（`"__favorites__"`）／`MEMO_FOLDER_ID`（`"__memo__"`）という**固定文字列ID**を持つ。いずれもユーザーによる削除・リネーム・移動はできない。

固定IDを採用した理由：表示名（`name`。ユーザーが変更可能）で予約フォルダを参照すると、名前変更や多言語化時に参照が壊れる。IDで参照すれば `name` は自由に変更できる。

**バリデーションはフロントエンドだけでなく Rust 側（保存直前）でも必ず行う。** 予約フォルダの整合性保証は、起動時に加えて保存コマンド内でも毎回実行し、フロントエンドから送られてきた配列に予約フォルダの改変（削除・リネーム・親付け替え）が含まれていても正しい値へ強制的に是正する。これは「UI 側で編集不可にするだけでなく Rust 側でも防御する」という、検索フォルダの階層数の範囲チェック等でも一貫して採っている方針である。

## ピン止めとお気に入りの構造上の違い

ピン止めは `PINNED_FOLDER_ID` の直下にしかノードを追加しない運用のため、データ構造上は隣接リストだが**実質的にはフラットな1階層リスト**として機能する。

お気に入りは `FAVORITES_FOLDER_ID` 配下に `type: "folder"` のノードを中間ノードとして自由に作成・ネストできる、**初めて「実際に木を組む」機能**である。

この違いにより、お気に入りでは「祖先チェーンをたどる子孫判定」「ツリーの平坦化」「登録時の配置先フォルダ選択」という3つの概念が新たに必要になった。ピン止めにはいずれも存在しない（配置先を選ぶという概念自体がなく、常に `PINNED_FOLDER_ID` 直下に追加するだけ）。

**今後メモ機能を実装する場合の判断**：メモを単純な一覧（ピン止め型）にするか、フォルダ分類を持つツリー（お気に入り型）にするかで、上記3概念の要否が変わる。フォルダ分類を持たせるなら、いずれもお気に入りの実装をそのまま再利用できる設計になっている。

<a id="duplicate-folder-name-validation"></a>

## 同一階層内の同名フォルダを禁止する

**同一の親フォルダ配下に、同名（トリム後・大小文字を区別しない）のフォルダを重複作成できない。** フォルダ作成・リネームの両方に適用する。

このバリデーションを設ける理由は、単なるデータの一意性のためではない。**同一階層に同名フォルダが複数存在すると、ユーザーが登録ダイアログのフォルダ選択で区別できず、意図と異なる方のフォルダを選んでしまう**（結果として「並び順がおかしい」といった別の症状として報告される）実例があったため。表示上の識別性が担保されていないツリーは、内部のアルゴリズムが正しくてもユーザー体感としての不整合を生む。

**関連する運用上の指針**：ツリー構造を持つ一覧で「順序がおかしい」「意図した項目と違うものが選ばれる」という報告を受けた場合、まずアルゴリズム（平坦化・ソート）自体を疑う前に、同名・同一表示内容のノードが複数存在してユーザーが取り違えていないかを先に確認すること。

<a id="favorite-mode-ordering"></a>

## お気に入りの並び順は再整列しない

お気に入りの一覧は、ファイル検索結果のような機械的な並び替え（frecency・アルファベット順等）を**一切行わず**、`order` フィールドが示す通りの並び順をそのまま表示する。

**フォルダとファイルを種別ごとにグルーピングせず、同一階層内で自由に混在・入れ替え可能とする。**

理由：お気に入りは「少数を厳選して登録する」用途である。機械的な整列（種別ごとにまとめる等）は、ユーザーが意図して行った手動の並び替えを無意味化してしまう。「大量の項目から目的のものを見つける」ファイル検索結果とは用途が異なり、お気に入りではユーザー自身が並び順そのものに意味を持たせたいはずだという判断から、システム側で並び順を再解釈・再整列しない。

<a id="favorite-edit-virtual-root-row"></a>

## お気に入り編集ビューの仮想固定行

お気に入り編集ビューは、一覧の先頭に**実体を持たない仮想固定行**（表示名「お気に入り」）を常時表示する。

- **目的**：「フォルダを選択 → その配下に作成」という既存ルールの下では、ルート直下に新規フォルダを作る手段が存在しない。この行がルート階層そのものを表す選択対象になることで解決する
- **制約**：実体を持たないため、リネーム・削除・★解除の対象外
- **絞り込み中も表示を維持する**（ルート直下への新規作成操作自体は絞り込み中でも成立するため、隠す理由がない）
- **ルートの表現には既存のセンチネル値 `FAVORITES_FOLDER_ID` をそのまま使い、専用の仮想ID（`"__root__"` 等）を新設しない**。`FAVORITES_FOLDER_ID` は元々ツリー走査の起点・フォルダ作成のデフォルト先・移動先バリデーションの全てで「ルート」として扱われていたため。**新しいセンチネル的な値を導入する前に、既存の値が流用できないかを必ず確認すること**
- **共有データを汚染しない**：仮想固定行は `/favorite` ブラウジング側の共有ツリーには含めず、編集ビュー専用の合成ツリーとしてのみ存在させる

## 検索フォルダごとの詳細設定のデータ構造

検索フォルダ（`FolderEntry`）は、`path`/`enabled` に加えてフォルダごとの詳細設定を持つ。

| フィールド | 型 | デフォルト | 備考 |
| --- | --- | --- | --- |
| 検索階層数 | 数値 | 3 | 有効範囲 1〜20。範囲外はエラーとし保存しない |
| フォルダ自体を検索対象に含めるか | 真偽 | `false` | |
| 拡張子フィルタのモード | `blacklist` \| `whitelist` | `blacklist` | |
| ブラックリスト拡張子 | 文字列配列 | 空 | 空リストなら常に許可 |
| ホワイトリスト拡張子 | 文字列配列 | 空 | 空リストなら常に拒否 |

**ブラックリスト用・ホワイトリスト用は必ず独立したフィールドとして持つ。** 共有の1フィールドにしてモードで解釈を切り替える方式は採用しない（モード切替時に入力内容が意図せず流用され、ユーザーが設定したつもりのない条件が適用される事故を防ぐため）。**今後、同種のモード切替を持つ設定を新設する場合も、モードごとに独立したフィールドを持たせること。**

**後方互換の方針**：新規フィールドはすべてデフォルト値付きで定義し、旧バージョンで保存されたエントリ（これらのキーを持たない）を読み込んだ場合はデシリアライズ時にデフォルト値が自動的に補われるようにする。**専用のマイグレーション処理は書かない。**

**拡張子フィルタの境界条件**：`*` のような全許可の特殊タグは実装しない。拡張子を持たないファイルは、ブラックリストでは（個々のタグに一致しようがないため）許可、ホワイトリストでは（同じ理由で）拒否となる。
