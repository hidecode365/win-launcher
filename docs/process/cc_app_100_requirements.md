# 100_要件定義 — CC実施要領

工程定義表全体は [WORKFLOW.md](../../WORKFLOW.md) を参照。本ファイルは 100_要件定義 工程における CC（Claude Code）自身の実施要領のみを扱う。100_要件定義は「要求の言語化」→「事前調査」→「要件確定・REQUIREMENTS.md反映」の3段階を持ち、CC が関与するのは主に後半の「事前調査」「要件確定」の2段階である。

## INPUT

- CA からの事前調査照会、または解釈確認依頼
- 現状の `REQUIREMENTS.md`（自動ロードされないため、回答前に必ず自分で読むこと。CA の起草文だけを鵜呑みにしない）

## 事前調査と解釈確認の違い

CA からの照会は必ずどちらかの区分が明示されて届く（区分の明示自体が運用ルール。詳細は WORKFLOW.md「100_要件定義」節を参照）。区分が明示されていない照会を受けた場合は、どちらの粒度で答えるべきかをCAに確認してから回答すること。

- **事前調査**：要件文がまだ確定していない、あるいはまだ存在しない段階での照会。`REQUIREMENTS.md` の該当節がまだ無いか、直近の確定済み隣接節のみが手がかりになる。既存設計・実装への影響範囲や実装コストの見積もりが主眼で、「この要件はこう解釈する」という確定的な回答ではなく、「この方向で進めた場合こういうコスト・影響が見込まれる」という見積もりを返す
- **解釈確認**：CAが起草した要件案が既に存在し、その解釈がCCの実装イメージと一致しているかを確認する段階。以下の「解釈確認で確認すべき観点」に従う

どちらの区分でも、回答を `DESIGN_LOG.md` に記録すべきかどうかはCAが依頼のたびに明示する（事前調査段階の結論は要件未確定の"生煮え"であることが多いため、記録要否を自動判定しない。明示が無い場合は記録しない）。

## 解釈確認で確認すべき観点

CA から要件案が届いたら、以下の3点を必ず検討したうえで回答する。

1. **実装可能性**：既存のアーキテクチャ・Tauri コマンド構成・プラグイン選定で実現できるか。大きな設計変更が必要になる場合は、その旨と概算の影響範囲を明記して返す
2. **既存仕様との整合**：追加・変更しようとしている要件が、現状の `REQUIREMENTS.md` の他の記述や `CLAUDE.md` の「設計原則ダイジェスト」節と矛盾しないか
3. **曖昧箇所の指摘**：要件文が複数の実装解釈を許す場合、その分岐点を具体的に示し、どちらの解釈で進めるかを CA・ひでさんに委ねる（自分で片方を勝手に決めて実装に進まない）

回答は「この要件はこう実装解釈することになるが良いか」という形で、実装イメージが伝わる粒度で書く。

## OUTPUT

- 事前調査への回答、または解釈確認への回答
- `REQUIREMENTS.md` の実際の編集（CA からの更新指示を受けてから行う。編集主体は CC。旧 `CLAUDE.md` にあった「基本的にユーザが行う」という記述はこの運用変更に伴い撤廃済み）
