# 200_設計 — CC実施要領

工程定義表全体は `WORKFLOW.md` を参照。本ファイルは 200_設計 工程における CC（Claude Code）自身の実施要領のみを扱う。

## INPUT

- MG の設計案（過去の関連議論の要約を含む）
- `DESIGN_LOG.md`
- 現状の `external-design/*.md`（自動ロードされないため、CC 自身が明示的に読む）
- 関連する `docs/internal-design/*.md`（同上。CC 自身が対象領域を判断し明示的に読む）

## 期待される振る舞い

単なる実装可否の判定に留めず、設計そのものに意見すること。以下の観点で検討する。

1. 該当する `docs/internal-design/*.md` に、同種の設計判断が過去に検討・却下された記録がないか（例：OCR 前処理による精度改善は検証済みで却下・見送り確定、といった記録）。あれば指摘し、同じアプローチを再検証しない
2. `CLAUDE.md`「設計原則ダイジェスト」節の既存原則と矛盾しないか（例：選択状態は導出値であり書き込み可能な state にしない、「1回だけ抑止する」フラグを安易に新設しない、等）
3. 実装後に生じうる副作用・エッジケース
4. 懸念が無い場合も「懸念なし」と明記する（沈黙を懸念なしと解釈させない）

## 外部設計書の更新（この工程での連携責務）

ドキュメント3層のうち、**外部設計書（`external-design/`）を更新するのはこの工程である**（層の定義は `CLAUDE.md`「ドキュメント構成（3層）」節を参照）。ただし編集主体はMGであり、ADは実装可能性・既存設計との整合性・副作用を批評する。内部設計書は 500_リリース前作業 で最新化するため、この工程では触らない。

- 設計の結論が**アーキテクチャ判断・状態遷移・データ構造の定義**に該当する場合、ADは対応する`external-design/*.md`への更新提案をhandoff経由でMGへ報告し、MGが更新する
- 外部設計書は PO が濃厚にレビューする対象のため、**AD の判断だけで変更を確定しない**。MGは更新内容について必ず PO 承認を得る
- 「これは外部設計に該当するか、内部設計に留まるか」の判断に迷った場合、勝手に決めずMGへ報告して判断を仰ぐ

## OUTPUT

- 設計への批評（懸念なしの場合もその旨を明記）
- `DESIGN_LOG.md` への追記。トピック単位の見出しで区切り、既存トピックの見出しがあれば追記、無ければ新設する
- 外部設計書への更新提案・実装後に判明した設計との差異の報告（該当時。handoff経由でMGへ通知）

## 実施上の限界の自覚

CC はセッションをまたいで文脈を保持しない。したがって批評の質は、MG が過去の関連議論をどれだけ要約して渡すかに強く依存する点は変わらない。ただしMGはリポジトリを直接ローカルで読めるため、CA時代のraw取得に伴う鮮度・キャッシュ問題は前提として消滅している。要約が不足していると感じた場合は、まず `DESIGN_LOG.md`・関連する `docs/internal-design/*.md` を自分で確認し、それでも情報が不足する場合は MG に追加情報を求める。
