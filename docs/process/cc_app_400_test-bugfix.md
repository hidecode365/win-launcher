# 400_テスト(バグ修正) — CC実施要領

工程定義表全体は [WORKFLOW.md](../../WORKFLOW.md) を参照。本ファイルは 400_テスト(バグ修正) 工程における CC（Claude Code）自身の実施要領のみを扱う。

## INPUT

- CA からの調査依頼

## 手順

手順の正本は `CLAUDE.md`「バグ修正フロー」節の7ステップであり、本ファイルでは重複記載しない。要点のみ引用する。

1. 症状の再現条件の切り分け（毎回起きるのか、特定条件依存か）
2. 直接原因の特定
3. 横並び調査（grep 等で機械的に洗い出す。思いつく範囲のリストアップで済ませない）
4. 原因の性質判定（個別実装ミスか、構造的な弱さか。個数によらず初回から判定する）
5. 個別対応 or 全体設計見直しの実施
6. 検証範囲の明示
7. 知見の型化（個別事例は該当する `docs/internal-design/*.md` の「経緯」節へ、再利用可能な原則のみ `CLAUDE.md` へ。この反映自体は 500_リリース前作業 工程で行う）

## 差し戻し先判断の材料

CA が 100/200/300 いずれかへの差し戻しを判断する材料として、原因分析結果に以下を添える。

- 原因が要件の曖昧さに起因する → 100_要件定義 を提案
- 原因が事前調査段階（100内）での実装コスト・影響範囲の見積もり誤りに起因する → 100_要件定義 を提案（200_設計ではなく100内の事前調査へ差し戻す）
- 原因が設計判断の誤りに起因する → 200_設計 を提案
- 原因が実装ミスのみに起因する → 300_実装 を提案

複数の指摘に異なる差し戻し先が付いた場合、それらを1本のプロンプトにまとめるなら最も上流（番号の小さい方）に揃える。100が1件でも含まれるなら全体を100として扱う。この判定は、CAが指摘を1本のプロンプトにまとめて送った場合にのみ適用する。個別に分割して送った場合は、各指摘の差し戻し先をそのまま使う。

## OUTPUT

- 原因分析結果（差し戻し先の提案材料を含む）
- 対処案
- 修正済みコード
