# ピン止め・お気に入りアイコンとツールチップ

対象コード: `src/components/IconSlot.tsx`（行末アイコン群の箱サイズ・ホバー円・Tooltipを一括管理する共通ラッパー）、`src/components/ToggleIcons.tsx`（`PinIcon`／`FavoriteIcon`／`WarningIcon`／`PinToggleButton`／`FavoriteToggleButton`）、`src/components/Tooltip.tsx`、`src/components/FavoriteTreeVisuals.tsx`（`CreateFolderIcon`・`FileIcon`・`HEADING_ROW_ICON_CLASS`／`CONTENT_ROW_ICON_CLASS`。お気に入り画面・メモ画面が共有する行頭アイコンの余白定数）、`src/components/ResultList.tsx`・`src/components/FavoriteEditTree.tsx`・`src/components/MemoManageView.tsx`（各行末・行頭アイコン群の呼び出し元。`IconSlot`＋`gap-2`のflexコンテナ、`HEADING_ROW_ICON_CLASS`／`CONTENT_ROW_ICON_CLASS`で束ねる）。

データ構造・機能仕様は [favorites-data-model.md](favorites-data-model.md) を参照。本ファイルはアイコンの意匠・視認性・ツールチップという UI 表現に特化した設計判断を記す。今後アイコンを追加・変更する際は、まず「今後の指針」節の一般原則を確認すること。

## 現在の設計

<a id="toggle-icon-visibility"></a>

### トグルアイコンの表示条件（selected のときのみ表示）

ピン止めブロック（`pinnedVisible` の一覧。全行が既にピン止め済み）・`/favorite` 一覧（全項目が登録済み）の★・ピンアイコンは、**選択中（`isSelected`）のときのみ表示する**。理由：一覧の全項目が既に登録済みであることが自明な文脈で常時表示すると、状態を区別しない単なる装飾になるため。

通常の検索結果行（こちらは「選択中、またはピン止め/お気に入り済み」の条件）と合わせ、3箇所すべてでアイコンの表示条件の考え方が統一されている：**「登録済みかどうかを見せる必要がない文脈（一覧の全項目が登録済みであることが自明な文脈）では selected のときだけ見せる」**というルールとして今後も踏襲すること。

<a id="toggle-icon-shape-and-color"></a>

### トグルアイコンの形状・配色ルール

`PinIcon`／`FavoriteIcon` は `filled: boolean` prop を受け取り、塗りつぶし版（`fill="currentColor"` のみ、輪郭線なし）と、輪郭版（`stroke="currentColor"`／`stroke-width="40"`／`fill="none"`。線画版素材のジオメトリを使用し、`viewBox="-20 -20 552 552"` で線幅のはみ出し分を吸収する。塗りつぶし版の `viewBox="0 0 512 512"` に合わせて書き換えてはならない）を切り替える。

- **状態はピン止め済み/未ピン止め（★登録済み/未登録）を色ではなく形状（輪郭／塗りつぶし）で表現する。**
- サイズは `w-4 h-4`（16px、Tailwindの既定クラス）。ピン（輪郭版・塗りつぶし版で異なる `viewBox`）と★を同じ表示サイズで揃えるため、`width`/`height` 相当のクラスを両方に明示的に同じ値で指定している（`viewBox` を揃えても表示サイズが揃うわけではない点に注意）
- 状態と配色（`toggleIconColorClass`。ピン・★共通の名称）：色は状態の表現に使わないため、「非選択→`text-gray-600`」「選択中→`text-white`」の2値のみ。色でON/OFFを表現せず、`filled` prop（形状）だけが状態を担う
- ツールチップ文言は「ピン止めに追加」／「ピン止めから削除」（★は「お気に入りに追加」／「お気に入りから削除」）で統一する
- アイコン単体のホバー反応：行の選択とは独立して、マウスカーソルがアイコンそのものの上に乗ったときだけ、`rounded-full` の背景をうっすら表示する（`hover:bg-black/[6%]`＝白系行、`hover:bg-white/20`＝選択中の青ハイライト行）。行の選択状態（背景色・`isSelected`）そのものは変えない、アイコン単体への視覚フィードバック

<a id="warning-icon"></a>

### 警告アイコン（実体が見つからない行）

塗りつぶし三角形＋「!」部分を `fillRule="evenodd"` の穴抜きで表現する（`WarningIcon`、`WARNING_ICON_PATH`）。穴の部分は常に行の背景色がそのまま透けて見えるため、「!」の可読性が行の3状態（通常／選択中／グレーアウト）のどの背景でも自動的に確保される（背景ごとに個別に色を出し分ける必要がない）。三角形本体の色は `text-amber-600`（非選択）／`text-amber-200`（選択中の青背景で視認できるよう明るい色）。塗りつぶしアイコンには半透明の暗色（`FILLED_ICON_OUTLINE_COLOR = rgba(0,0,0,0.35)` 前後）の `stroke` を追加し、塗り本体の色を変えずに輪郭だけ明確にする（半透明の黒はどの背景色に対してもある程度沈んで見えるため、背景ごとの縁取り色の出し分けが不要）。

サイズは `w-4 h-4`（ピン・★アイコンと同サイズ）。

実体が存在しない行（グレーアウト対象）でも、警告アイコン・ピンアイコン（トグルボタン）自体は `opacity-50` の対象から明示的に除外している（グレーアウトはファイルアイコン・ファイル名・パス部分にのみ適用する）。選択中であれば「選択中・ピン止め済み」の配色がそのまま適用され、手動でのピン止め解除操作ができる。

<a id="tooltip-component"></a>

### ツールチップ表示（`Tooltip` 共通コンポーネント）

UI 上の操作部品にツールチップを付ける場合、`title` 属性は使わず、必ず共通コンポーネント `Tooltip`（`src/components/Tooltip.tsx`）を使う。今後実装予定のメモ機能のノートアイコンでもこの同じコンポーネントを使い回すこと（機能専用の実装にしない）。

**API**：`<Tooltip label="表示する文言" className="呼び出し元のレイアウトクラス">{子要素}</Tooltip>` の形で子要素をラップする。`Tooltip` 自身は `relative inline-flex` の `<span>` を1枚追加するだけの薄いラッパーのため、元々ラップ対象が直接持っていたレイアウト用クラス（`ml-2`／`flex-shrink-0` 等、Flex コンテナ内での配置に関わるもの）は `className` prop 経由で `Tooltip` 側に渡し、子要素自身は見た目（丸み・パディング・色）のみを持つ形に分離する。

**仕様**：

- 表示までの遅延は300ms。マウスホバー開始から `setTimeout` で計測し、300ms経過時点でまだホバーが続いていれば表示する
- 非表示はマウスが離れた時点で遅延・アニメーションなしに即座に行う（表示中のタイマーが残っていれば `clearTimeout` で確実に破棄する）。表示・非表示で振る舞いが非対称（片方は遅延あり、片方は即座）なため、単一の CSS `transition` では表現せず、`visible` state による条件付きレンダリングの有無で切り替えている
- 表示のきっかけはマウスホバーのみ（`onMouseEnter`/`onMouseLeave`）。キーボードによる選択（`onFocus` 等）では表示しない
- 表示位置は既定で対象要素の左側・垂直方向中央固定（`right-full top-1/2 -translate-y-1/2`）。右端に配置される操作アイコン向けの既定値
- 見た目：背景 `bg-gray-800`、文字は白・`text-xs`（12px）、`rounded-md`、パディング `px-2 py-1`。アニメーションは付けていない（表示・非表示の非対称な振る舞いをシンプルに保つため）
- コンポーネント自身がアンマウントされる場合（対象行が一覧の再構築で消える等）に備え、表示待ちタイマーを `useEffect` のクリーンアップで確実に破棄する

**表示位置の例外（`side` prop）**：既定の左側表示は、対象要素自身が画面左端に近い場合には逆に画面外へはみ出す。`Tooltip` に `side?: "left" | "right"`（デフォルト `"left"`）prop があり、画面左端に近い対象（ピン止めブロックのドラッグハンドル、設定パネルの戻るボタン等）は `side="right"` を指定して右側表示に切り替える。**新しい呼び出し元を追加する際は、対象要素が画面（ウィンドウ）左端に近い位置にあるかどうかを確認し、近い場合は `side="right"` を指定すること。**

**`title` 属性を許容する例外**：ツールチップが「操作の説明」ではなく「省略表示された内容の全体を見せる」目的の場合（例：`FileSearchSettings.tsx` の `FolderPathButton` の `title={path}`。中央省略された検索フォルダパスの完全な文字列を見せるためのもの）は、`Tooltip` への置き換え対象から除外し `title` 属性のままでよい。理由は2点：(1) 対象要素自体に既に表示テキストがあり、`title` 属性の遅延・表示位置の問題が操作アイコンほど致命的でない、(2) 長いパス文字列を `Tooltip` の固定幅デザイン（`whitespace-nowrap`、小型バッジ）に載せると、幅や折り返しの調整が別途必要になり `Tooltip` 自体の汎用性を損なう。**「アイコンのみで操作を表す要素」と「省略テキストの全体表示」は目的が異なるため、機械的に全ての `title` を置き換えるのではなく、この2区分で判断すること。**

**適用状況（棚卸し・v0.10.0時点）**：

- ピンアイコン（`PinToggleButton`）：「ピン止めに追加」／「ピン止めから削除」。`side` 既定（左）
- ピン止めブロックのドラッグハンドル：「ドラッグして並び替え」。`side="right"`
- 警告アイコン（`WarningIcon`）：「実体が見つかりません」。`side` 既定（左）
- 検索ボックスの設定アイコン（`SearchBox.tsx`）：「設定」。`side` 既定（左）
- 設定パネルの戻るボタン（`SettingsPanel.tsx`）：「戻る」。`side="right"`
- ファイル検索タブの検索フォルダ一覧（`FileSearchSettings.tsx`）：詳細設定アイコンに「詳細設定」、削除アイコンに「このフォルダを検索対象から削除」。いずれも `side` 既定（左）
  - 検索フォルダのフルパス表示（`FolderPathButton` の `title={path}`）のみ、上記の「`title` 属性を許容する例外」に該当するため対象外
- 上記5箇所はいずれも `overflow-y-auto`（一部は入れ子）を持つスクロールコンテナ内・またはウィンドウ全体の角丸クリップ（`overflow-hidden`）の影響下にあるが、対象アイコンがコンテナの左端から十分離れた位置にあるため、ツールチップの表示幅がコンテナ境界を超えないことを寸法計算で確認済み（実機での目視確認は `npm run tauri dev` を起動しない方針のため未実施。ウィンドウの最小サイズ 640×420 でも成立することを前提に計算した。より長い文言を持つ対象を追加する場合は、この計算を同様に行うか、実機で確認すること）

<a id="icon-slot-wrapper"></a>

### 行内アイコンの共通ラッパー化（IconSlot）

行末に並ぶアイコン群（ピン・★・件数バッジ・フォルダ作成・削除）は、共通コンポーネント `IconSlot`（`src/components/IconSlot.tsx`）を経由して描画する。個々のコンポーネントやJSXが独自に `ml-2` 等の個別マージン・ホバー円・Tooltipラップを実装することは禁止し、以下の2契約に統一する。

- **箱のサイズは種別によらず同一**：`interactive`（クリック可能：ピン・★・フォルダ作成・削除）・`interactive={false}`（表示専用：件数バッジ等）のいずれも、`w-6 h-6`（明示的な24×24px、border-box）＋`rounded-full p-1` の同じ「箱」を持つ。表示専用要素は背景・Tooltipを持たないだけで、箱の外形サイズは揃える。**箱のサイズは `w-6 h-6` で明示的に固定し、子要素の実寸から自動計算させない**（子要素が `absolute` 化されて通常のレイアウト計算から除外されると、根拠となる in-flow の中身が無くなり `p-1` の分だけに縮む不具合を経験したため。[icon-slot-wrapper-history](#icon-slot-wrapper-history) の6.を参照）
- **余白は個々の要素ではなく、それらを束ねる親のflexコンテナの `gap-2` で表現する**：`IconSlot` 自体はマージンを一切持たない。呼び出し元（`ResultList.tsx`・`FavoriteEditTree.tsx`・`FavoriteListPanel.tsx`の各行）は、行末のアイコン群を `<div className="flex items-center gap-2 ml-2">` で1つに束ね、行の内容部分との間隔だけをこの外側の `ml-2` で取る
- `interactive` 時は `onClick` に対して `stopPropagation` を`IconSlot` 内部で行うため、呼び出し元は行全体のクリックハンドラ（起動・折りたたみ等）を気にせず渡してよい
- `WarningIcon` は例外的に `IconSlot` に乗せない（`w-5 h-5`・amber系という他のアイコンと異なる独自のサイズ・配色を持つため）。ただし個別マージン（旧 `mr-1`）は撤去済みで、他のアイコンと同じく呼び出し元の `gap-2` コンテナに委ねる
- 新しい行末アイコンを追加する場合、この2契約（箱のサイズ統一・余白のgap一本化）から外れる独自実装をしないこと。判断に迷った場合はまず既存の呼び出し例（`FavoriteEditTree.tsx` の折りたたみ行）を参照する

<a id="heading-and-content-row-icon-class"></a>

### 行頭アイコンの余白（`HEADING_ROW_ICON_CLASS`／`CONTENT_ROW_ICON_CLASS`）

行末アイコン群（IconSlot）とは別に、行の先頭（ドラッグハンドルの直後）に置くフォルダ／ファイル種別アイコンの余白も、行の種類に応じた2パターンの共有定数（`FavoriteTreeVisuals.tsx`）へ統一している。

- **`HEADING_ROW_ICON_CLASS`**（`ml-1.5 mr-2 h-4 w-4 flex-shrink-0`）：フォルダ見出し行・ゴミ箱固定行など、チェブロン（▼/▶）の直後にアイコンが続く行で使う
- **`CONTENT_ROW_ICON_CLASS`**（`mr-3 h-4 w-4 flex-shrink-0`）：アイテム行・メモ行など、チェブロンを持たずドラッグハンドルの直後に直接アイコンが来る行で使う。**アイコン自身に左マージンを持たせない**（ドラッグハンドル自身の `mr-1.5` と二重に加算され、間隔が不自然に広がるため）
- コンテンツ行のフォールバックアイコン（サムネイル・実体画像を持たない行）には `opacity-60` を付与する。お気に入りアイテム行のファイルアイコン（サムネイル無し時）・メモ画面のメモ行アイコン（常にフォールバック）の両方がこの対象

## 経緯

<a id="filled-outline-icon-design-history"></a>

### ピンアイコンの意匠変更（写実路線の撤回 → 提供SVG素材のシルエットへの統一）

視認性改善の後、意匠そのものを複数回作り直した。

1. 参考画像（青系の画鋲。頭部の丸い受け皿・円柱状の軸・軸下部のつば（フランジ）・先端が尖った針の4パーツ構成、濃紺の輪郭線＋鮮やかな青の本体＋白い光沢ハイライトという配色）をもとに、シルエットと明暗のバランスを再現した写実的な塗りつぶしアイコンを実装した（頭部楕円・軸・つば・針の4つの `<rect>`/`<path>` を個別の縁取り付きで重ね描きし、光沢ハイライトを別レイヤーの塗りつぶし図形2つで追加する構成）
2. 実装後、アプリ全体の見た目で確認したところ、**この写実的な意匠（複数パーツ・光沢ハイライト・固定の配色パレット）が、隣接するテキストベースのフラットな検索結果行と比べて主張が強すぎ、アプリ全体のミニマルな雰囲気に合わない**という判断に至った。視認性そのもの（コントラスト・サイズ）は改善できていたが、「視認性」と「意匠の重さ・主張の強さ」は別軸の問題であり、片方を解決してももう片方が新たな課題になり得るという教訓が得られた
3. 対応として、写実的な複数パーツ構成・光沢ハイライト・固定配色パレットをすべて廃止し、丸みを帯びた頭部のカプセル形状＋細い針の2パーツのみを自作した、シンプルな線画スタイル（`currentColor` 追従の単色）に全面的に描き直した
4. その後、ユーザーから単色（`#4B4B4B`）・グラデーションなし・装飾なしの「花形の頭部＋針」のフラットなピクトグラムSVG素材（ICOOON MONO「押しピンのアイコン素材」）が提供されたため、自作の簡略図形（角丸長方形2つ）をやめ、**この素材のシルエット（実際の `path`/`polygon` の座標データ）をそのまま流用する**形に統一した。既製の意匠アセットが提供された場合は、似た形を自作で近似するより、そのアセットのジオメトリを直接使う方が形状の再現性が高く、かつ実装上の判断（角度・比率等の微調整）を減らせるため
5. 上記4の時点では、素材本来の単色フラットな設計を離れ、濃紺の輪郭線＋青の本体という固定の二色パレットを後付けしていた。その後、**この二色構成が素材本来の設計（`fill:#4B4B4B` の単色シルエット、輪郭線を持たない）から外れていること、また検索結果行の中でドラッグハンドルやパス表示がニュートラルなグレー階調で統一されているのに対し、ピンアイコンだけが高彩度の二色構成を持ち、操作部品でありながらコンテンツ（ファイルアイコン）と同等以上の視覚的な重さを持ってしまっていたことが問題として指摘され、単色化（`fill="currentColor"` のみ、輪郭線なし）に方針転換した**。あわせて、行の状態を「非選択」「選択中」の2つに統一し（本アプリはマウスホバーで選択行そのものが移動するため、「ホバー中」と「選択中」は同一状態であり、ホバー専用のスタイル分岐を廃止できる）、ピン止め済みかどうかは色相ではなく濃淡で表現する方式に切り替えた

その後、00-requirements.md「アイコンによる状態表現の共通規則」節の仕様変更に伴い（お気に入り機能の実装・段階2）、ピン止め済みかどうかの表現を上記の「色の濃淡（3値）」から「形状（輪郭／塗りつぶし）」へさらに変更した（現在の設計。[toggle-icon-shape-and-color](#toggle-icon-shape-and-color) 参照）。これはピン止めだけでなく、同時に新設したお気に入りの★アイコンとも共通のルールである。単色シルエットから輪郭／塗りつぶしの切り替えへ移行するのに合わせ、サイズも 18px → 16px へ一段引き下げた。理由はサイズ自体の視覚的な重さの調整ではなく、同じ行に並ぶ★アイコン（お気に入り）と描画サイズを完全に統一するため（viewBox が異なる2つの形状を同じ表示サイズで揃えるには、`width`/`height` 相当のクラスを両方に明示的に同じ値で指定する必要がある）。

<a id="icon-visibility-improvement-history"></a>

### アイコンの視認性改善で見つかった3つの落とし穴

意匠変更後の見た目レビューで、警告アイコン・ピンアイコンの視認性に関する指摘が3件あり、修正した。**アイコンは「単色を一律適用する」のではなく、行が取りうる背景状態（通常／選択中／グレーアウト）ごとに個別にコントラストを検証する**という設計原則が、この3件から導かれた。

- **問題の背景**：`ResultList.tsx` の行は「通常（白／薄いグレーhover）」「選択中（`bg-blue-500` の青ハイライト）」「グレーアウト（ピン止め先の実体が見つからない）」の3状態を取りうる。単一の色・不透明度をアイコンに設定すると、必ずどれかの背景で埋没する
- **警告アイコン**：以前は輪郭線のみ（`fill="none"`、`stroke` 細め）の三角形だったため、遠目には判別しづらかった。塗りつぶし＋穴抜きの「!」方式（[warning-icon](#warning-icon) 参照）に変更した
- **グレーアウト行の落とし穴**：ピン止めブロックの行全体に `opacity-50` を掛けて「実体なし」を表現していたため、警告アイコン自体もその不透明度に巻き込まれ、色・形状をいくら改善しても効果が薄れる構造になっていた。**「視覚的に目立たせたい要素」と「視覚的に控えめにしたい要素」が同じ行の中に混在する場合、`opacity` はそれらをまとめて持つ共通の祖先要素ではなく、控えめにしたい要素側（ファイルアイコン・ファイル名・パス）だけを囲む内側の要素に付与すること。** 警告アイコン・ピンアイコン（トグルボタン）はこの `opacity-50` の対象から明示的に除外した
- **ピンアイコンが選択中の行で背景に同化する問題**：`PinToggleButton` は「非ピン止め・非選択の行ではホバー時のみ薄く表示する」ためのフェード演出として `opacity-60`〜`opacity-100` を使っていたが、この演出が「選択中（青ハイライト）だが未ピン止めの行」にもそのまま適用され、白系アイコン×青背景×60%不透明という低コントラストな組み合わせを生んでいた。**「ホバーで薄く見せる」という演出上の都合と、「選択中の行では常にはっきり見せたい」という要件は別軸であり、混ぜて1つの opacity ロジックに詰め込むと片方を満たせば片方が壊れる。** 修正では `active || selected`（ピン止め済み、または行が選択中）なら常に `opacity-100`、それ以外（非選択・未ピン止め）の場合のみホバー時フェードを適用する形に分離した

### `title` 属性から `Tooltip` 共通コンポーネントへの置き換え経緯

ピンアイコンのツールチップは当初 `title` 属性で実装していたが、以下2点の問題があり独自コンポーネントに置き換えた。

- **表示遅延を制御できない**：`title` 属性のツールチップ表示までの遅延（500ms〜1秒程度）は WebView2（ブラウザ）の固定挙動であり、CSS/JS からは変更できない。体感として遅く感じる
- **表示位置がカーソル依存**：`title` はマウスカーソルの位置を基準に表示されるため、画面右端に配置されるアイコン（ピンアイコンは行の右端）では表示位置が不自然になりやすい

警告アイコンについても、以前は SVG の `<title>` 要素を使っていたが、これも HTML の `title` 属性と同じ表示遅延・表示位置の問題を持つブラウザ既定の仕組みであり、同様に `Tooltip` へ置き換えた。

### フォルダ作成アイコンの自作合成を2回試作したが断念し、既製素材へ切り替えた経緯

お気に入り編集ビュー（軸4f）のフォルダ作成アイコンは、当初「既存の塗りつぶしフォルダアイコン（`FOLDER_ICON_PATH`）に小さな『+』を合成する」自作案を採用したが、実機確認で2回とも「+」が視認できないと判明し、既製素材への切り替えに至った。

1. **1回目の試作**：`FOLDER_ICON_PATH` に「+」形の2つの矩形（横長・縦長）を追加のサブパスとして重ね、`fillRule="evenodd"` によりフォルダ本体の塗りに対する穴として抜く方式を実装した。実機確認の結果、「+」が視認できないと報告された
2. **原因調査で判明した2つの不具合**：(1) 腕の太さ1.4 viewBox単位は、表示サイズ（`w-4 h-4`＝16px、viewBoxは `0 0 24 24` のためスケール比 16/24≈0.667）で実寸約0.93pxしかなく、ブラウザのアンチエイリアシングで実質潰れていた。(2) 2つの矩形サブパスが交差する中央部分は、evenoddの交差回数が奇数→偶数→奇数と変化するため「穴の中に穴じゃない小さな正方形」ができてしまい、たとえ太くしてもクロス形状として綺麗に抜けない構造上の欠陥があった
3. **2回目の試作**：「+」を2つの矩形の重ね合わせではなく、12頂点の単一の閉じたポリゴン（自己交差なし）として1つのサブパスで表現し直し、腕の太さも4 viewBox単位（実寸約2.7px）に拡大した。理論上は(1)(2)とも解消されるはずだったが、実機確認では依然として視認性を確保できなかった（16pxという表示サイズ自体が、細部を描き分けるにはそもそも小さすぎた可能性が高い）
4. **既製素材への切り替え**：2回の試作でも解決しないため、自作合成を継続せず、ICOOON MONO の既製素材「フォルダアイコン12」（フォルダに「+」を組み合わせた既製デザイン）のジオメトリ（`path` 2つ：フォルダ本体＋「+」バッジ）をそのまま流用する方針に切り替えた。ピンアイコン（[filled-outline-icon-design-history](#filled-outline-icon-design-history) 4.）と同じ「既製素材が使えるなら自作で近似せず、そのジオメトリを直接使う」前例に倣う
5. **単色シルエット規約からの逸脱は無かった**：ダウンロードした素材は viewBox `0 0 512 512` の単色フラットシルエット（元データ `fill:#4B4B4B`）で、輪郭線を持たない塗りつぶし1色のみだった。依頼時点では「線画スタイルへの例外」を許容する想定だったが、実際に入手した素材は既存の塗りつぶしアイコン規約（`fill=currentColor`）とそのまま両立したため、規約上の例外扱いは結果的に不要だった

**教訓**：自作合成で視認性の問題が繰り返し発生する場合、座標の微調整を重ねるより、既製素材への切り替えを早い段階で検討すること。特に16px前後の小さな表示サイズでは、複数図形の重ね合わせ（今回の「+」合成のような）自体が視認性に対して構造的に不利であり、単一の完成されたジオメトリを流用する方が確実性が高い。

### 2回のマージン調整では直らなかった整列崩れと、IconSlotによる構造的解決の経緯

行末アイコン（★・ピン・件数バッジ・フォルダ作成・削除）のサイズ（`w-4 h-4`）・マージン（`ml-2`）の値を2回にわたって揃える個別対応を行った（軸4k・軸4l相当）にもかかわらず、実機確認で「まだ整列がずれて見える」という指摘が繰り返された。この節はその根本原因の診断結果と、個別対応から構造的な解決（IconSlot導入）へ切り替えた経緯を記録する。

1. **最初の仮説（誤り）**：SVGパスのジオメトリ自体が非対称で、視覚的な重心が `viewBox` の幾何中心からずれているのではないかと疑った。手作業での目算では `CreateFolderIcon` の合成パス（本体＋バッジ）が上下非対称（上マージン約9%・下マージン約22%）に見えたが、Node.jsで実際にSVGパス文字列をパースしbounding boxを計算するスクリプトを書いて検証したところ、実際にはほぼ左右上下対称（9.5%/9.5%）であることが判明した。**目算による視覚的な非対称の指摘は、実際に座標を計算して裏付けを取るまで信用しないこと**（このプロジェクトの一般原則。今回はこの検証により「ジオメトリの非対称」という誤った仮説を早期に排除できた）
2. **真の原因**：`w-4 h-4`・`ml-2` の値自体は既に統一されていたが、各アイコンの実際のDOM構造が2系統に分かれていた。(a) 「パディング付きボタン」パターン（`Tooltip` > `button`（`p-1`）> `svg`（16px）で実効フットプリントが24×24px相当）と、(b) 「素の要素」パターン（`p-1`を持たないプレーンな`span`。件数バッジ等）。両者は宣言上の `margin`（`ml-2`）が同じ値でも、隣接する要素がどちらのパターンかによって実際に見える隙間（8px/12px/16px相当、パディング付きボタン同士が隣接する場合とプレーン要素が挟まる場合とで加算される padding の個数が変わるため）が変わってしまい、これが「サイズ・マージンの値は揃っているのに整列して見えない」の正体だった
3. **個別対応で済ませなかった判断根拠**：この「パディング付きボタン／素の要素の混在」は特定のアイコン1つの実装ミスではなく、行末アイコン群全体が採用していた「各コンポーネントが各自のマージン・パディングを個別に持つ」という設計パターンそのものの構造的な弱点だった。値の再調整（3回目の個別対応）を重ねても、新しいアイコン種別を追加するたびに同じ問題が再発することが明らかだったため、CLAUDE.md「バグ修正フロー」節の「原因の性質を判定する」ステップに従い、個別対応ではなく全体設計の見直し（共通ラッパー `IconSlot` の新設）を選んだ
4. **解決**：`IconSlot` が「箱のサイズ（`interactive` の有無によらず `p-1` 込みで統一）」「ホバー円・Tooltip（`interactive` のときのみ）」を一括管理し、呼び出し元は個々のマージンを持たず、アイコン群を束ねる親要素の `gap-2` だけで余白を表現する設計に統一した（[icon-slot-wrapper](#icon-slot-wrapper) 参照）。表示専用要素（件数バッジ）も同じ箱サイズを持つ透明なラッパーに包むことで、「隣にボタン系があるかどうか」に関わらず実際の隙間が常に一定になる

**教訓**：「サイズ・マージンの数値を揃えたのに見た目が揃わない」という報告を受けた場合、まず疑うべきは数値そのものの誤りではなく、要素ごとに異なるDOM構造（パディングの有無・ラッパーの層数）による実効フットプリントの違いである。数値の再調整を繰り返す前に、実際のDOM/CSSボックスモデルを比較すること。

5. **IconSlot導入後も残った2つの不一致（実測で発覚）**：IconSlot導入後に各行の実寸を測定したところ、さらに2つの不一致が見つかった。調査時だけ使用した画面内計測オーバーレイと計測用属性は、500_リリース前作業で製品コードから撤去済みである
   - **件数バッジの背景円の直径が16のまま**：外形の「箱」は他のアイコンと同じ24×24に揃っていたが、バッジ自身の色付き円（`w-4 h-4`、16px）は箱の内側にそのまま収まっているだけで、箱いっぱいには広がっていなかった。`IconSlot` の箱に `relative` を付与し、バッジ側を `absolute inset-0` にすることで、箱自身の `p-1` パディングを無視して箱の外形（24px）いっぱいに広がるよう修正した（絶対配置要素の containing block は最も近い `position: relative` 祖先のパディングボックスになるため）。あわせて `/favorite` 一覧（`FavoriteListPanel.tsx`）側の桁数依存の可変幅ピル型バッジも、編集ビューと同じ固定サイズの円形に統一した（3桁までは実際の文字サイズで収まる想定。4桁以上は円からはみ出しても許容する）
   - **行末アイコンの右端の間隔が8px/16pxでずれる**：★が最後に来るアイテム行では16px、削除アイコンが最後に来るフォルダ行では8pxだった。原因はアイコン自身の個別マージンの消し忘れではなく、**行のルート要素自身の `padding-right`（`pr-2` と `pr-4`）が行の種別（フォルダ行／アイテム行）によって元々異なっていた**こと。IconSlot導入時に「アイコン間の間隔」は `gap-2` に一本化したが、「行の右端から最後のアイコンまでの間隔」は行自身のpaddingが担っており、この値の統一が漏れていた。全ての行を `pr-4`（16px）に統一して解消した

**教訓（追加）**：「アイコン間の間隔」と「行の右端から最後のアイコンまでの間隔」は別のCSSプロパティ（前者はflexコンテナの`gap`、後者は行ルート要素の`padding-right`）が担っている。整列の不一致を調査する際は、アイコン自身のマージンだけでなく、アイコンを内包する行・コンテナ側のpadding/marginも同様に横並び比較すること。

6. **件数バッジが円の直径24どころか8まで縮小した回帰（5.の修正直後に発覚）**：5.で件数バッジの子要素を `absolute inset-0` に変更した際、`IconSlot` の箱自体には明示的な幅・高さを指定していなかった（`p-1` 込みで子要素の実寸から自動的に24×24へサイズが決まる想定だった）。ところが `absolute` 化した子要素は通常のレイアウト計算（親のサイズ決定に使われる in-flow の内容物）から除外されるため、箱には「サイズを決める根拠となる中身」が無くなり、`p-1` の分（上下左右2px×4=8px）だけの大きさに縮んでしまった（実測 `W=H=circle=8` で確定）。修正は `IconSlot` の箱に `w-6 h-6`（24px、border-box）を明示的に指定し、中身が in-flow か `absolute` かに関わらず箱自体の外形サイズを固定することで解消した

**教訓（追加2）**：`p-1` 等のパディングだけを指定し、幅・高さを子要素の実寸に依存させて自動計算させる設計は、その子要素の描画方式（in-flow か `absolute`/`fixed` か）が変わった瞬間に暗黙的に壊れる。共通ラッパーのように「複数の異なる描画方式の子要素を受け入れる」コンポーネントでは、箱自体のサイズは子要素に依存させず明示的に固定すること。

### メモ行アイコンがドラッグハンドルから離れて濃く見えた不具合（issue 0026 補足修正）

**症状**：PO実機レビューで、メモ画面のメモ行だけアイコンが他の行より濃く見え、ドラッグハンドル（⋮⋮）とアイコンの間隔もお気に入り画面のアイテム行より広く見える、と報告された。

**直接原因**：2つの生値の不一致が重なっていた。(a) メモ画面のメモ行アイコン（`FileIcon`）は、フォルダ見出し行と同じ `ml-1.5 mr-2 h-4 w-4 flex-shrink-0` を流用していたが、フォルダ見出し行はチェブロンの後にアイコンが続くのに対し、メモ行はチェブロンを持たずドラッグハンドルの直後にアイコンが来る。ドラッグハンドル自身の `mr-1.5` とアイコンの `ml-1.5` が隣接要素同士で単純加算され、お気に入りアイテム行（アイコンに左マージンを持たせず `mr-3` のみ）の2倍の間隔になっていた。(b) お気に入りアイテム行はサムネイル無し時のフォールバックアイコンに `opacity-60` を付けているが、メモ行アイコンは常にフォールバック相当（メモはサムネイルを持たない）であるにも関わらず不透明度の指定が無く、フル濃度で表示されていた。

**横並び調査**：行頭アイコンを使う全箇所（お気に入りのフォルダ見出し行・アイテム行、メモのフォルダ行・ゴミ箱行・メモ行）のマージン・不透明度指定を比較した結果、上記2点以外に不一致は無かった（フォルダ見出し行同士・ゴミ箱行はチェブロンの後という同じ構造のため元々一致していた）。

**原因の性質**：特定の1行の実装ミスではなく、「行頭アイコンの余白・不透明度を各呼び出し箇所が生のTailwindクラス文字列として個別に持つ」という設計が、チェブロンの有無という行の構造差を考慮せずに値だけをコピーした結果生じた構造的な不一致と判断した。[icon-slot-wrapper-history](#icon-slot-wrapper-history) が行末アイコン群で辿った「個別マージン → 共有ラッパー化」と同じ教訓が行頭アイコンにも当てはまる。

**対応**：行の構造（チェブロンの有無）に応じた2つの共有定数 `HEADING_ROW_ICON_CLASS`／`CONTENT_ROW_ICON_CLASS`（`FavoriteTreeVisuals.tsx`）を新設し、両画面の該当箇所（お気に入りのフォルダ行・アイテム行、メモのフォルダ行・ゴミ箱行・メモ行の計5箇所）から参照する形に統一した（[heading-and-content-row-icon-class](#heading-and-content-row-icon-class) 参照）。フォルダ行・ゴミ箱行の見た目（既に一致していた）は変更していない。

## 今後の指針

- 新しいアイコンを追加・変更する際は、まず素材が単色フラットな設計として提供されている場合、その設計のまま（`fill="currentColor"` の単色塗り）使うこと。視認性対応のために独自の配色ルールを機械的に適用するのではなく、素材本来の設計を尊重する
- 検索結果行における役割分担：色を持つのはコンテンツ（ファイルアイコン等）のみとし、操作部品（ピン・★アイコン、ドラッグハンドル等）はニュートラルな階調（グレー／白の濃淡）に揃える
- 操作部品アイコンの色は、その行の文字色（`currentColor` 相当）に追従させる（白背景の行ではグレー、選択中の青ハイライト行では白）。状態（ON/OFF、登録済みかどうか等）は色相・濃淡ではなく形状（輪郭／塗りつぶし）で表現する
- トグル系アイコンは「現在の状態」を表示する。「押したらどうなるか」を斜線等の記号で追加表現しない（斜線はUI慣習上「禁止・無効」を意味し、トグルの意味が反転して伝わるため）。操作の示唆はツールチップと、アイコン単体のホバー反応（淡い円形背景等）で行う
- 本アプリではマウスホバーによって選択行そのものが移動するため、「ホバー中」と「選択中」は同一の状態として扱う。行の状態を「非選択」「選択中」の2つだけに統一し、`group-hover` 等のホバー専用スタイル分岐を作らない
- 単色シルエットは、同じ寸法でも二色構成（輪郭線＋本体）より視覚的な重さが増す。二色構成から単色化する際は、サイズを一段下げることを検討する
- 「視覚的に目立たせたい要素」と「視覚的に控えめにしたい要素（グレーアウト対象）」が同じ行に混在する場合、`opacity` は控えめにしたい要素だけを囲む内側の要素に付与する。共通の祖先要素に付与しない
- 新しい操作アイコンにツールチップを付ける場合は必ず `Tooltip` コンポーネントを使い、`title` 属性を使わない。ただし「省略テキストの全体表示」目的の場合は `title` 属性のままでよい
- 自作の合成アイコン（複数図形の重ね合わせ・穴抜き等）で視認性の問題が2回程度繰り返し発生した場合、座標の微調整を続けず、既製素材への切り替えを検討する（[create-folder-icon-readymade-history](#create-folder-icon-readymade-history) を参照）。特に16px前後の小さな表示サイズでは、複数図形の重ね合わせ自体が構造的に視認性に不利なため、単一の完成されたジオメトリを流用する方が確実性が高い
- 新しい行末アイコンを追加する場合は必ず共通ラッパー `IconSlot` を使い、個々のコンポーネントが独自の `ml-2`・ホバー円・Tooltipラップを実装しない（[icon-slot-wrapper](#icon-slot-wrapper) 参照）。「サイズ・マージンの数値は揃えたのに見た目が揃わない」という報告を受けた場合は、数値の再調整より先に各要素の実際のDOM構造（パディングの有無・ラッパーの層数）の違いを疑う（[icon-slot-wrapper-history](#icon-slot-wrapper-history) 参照）
- 表示専用の行内要素（件数バッジ等）の塗りつぶし部分を「箱」いっぱいに広げたい場合、`IconSlot` の `relative` な箱に対して `absolute inset-0` を指定する（箱自身の `p-1` パディングを無視して外形いっぱいに広がる）。行の右端から最後のアイコンまでの間隔は、アイコン自身のマージンではなく行ルート要素の `padding-right` が担うため、新しい行種別を追加する場合は既存の行（`pr-4`）と同じ値に揃える（[icon-slot-wrapper-history](#icon-slot-wrapper-history) の5.を参照）
- 新しい行頭アイコン（フォルダ／ファイル種別アイコン）を追加する場合は、行の構造（チェブロンの有無）に応じて `HEADING_ROW_ICON_CLASS`／`CONTENT_ROW_ICON_CLASS`（[heading-and-content-row-icon-class](#heading-and-content-row-icon-class) 参照）を使い、生のマージン値を個別にコピーしない。チェブロンを持たない行（ドラッグハンドルの直後にアイコンが来る行）のアイコンには左マージンを付けないこと（ドラッグハンドル自身のマージンと二重に加算される。[content-row-icon-margin-history](#content-row-icon-margin-history) を参照）。サムネイル・実体画像を持たず常にフォールバック表示になる行のアイコンには `opacity-60` を付け、他画面の同種フォールバックアイコンと濃度を揃える
