# MGからの指示の確認方法

MGからの指示・報告のやり取りは、このリポジトリ内ではなく
`../mng/handoff/ad.md`（mngリポジトリ配下）に書き込まれる。「MGの指示を確認して」
「対応して」などと言われたら、まずこのファイルを読むこと。着手報告・完了報告も
同じファイルの該当欄に書き込む。チャットでの完了回答は、完了報告の記入後に行う。

`DESIGN_LOG.md`を含むドキュメント編集タスクでは、完了報告の前に必ず `git add` → `git commit` → `git push` を実施し、pushされたことを確認する。未コミット・未pushの編集を完了として報告しない。

MG・ADは、割り当てられた作業だけでなく、気づいた工程・品質上の改善点をhandoffで相互に簡潔に指摘し合う。単発の指摘はその場の共有に留め、同種の問題が繰り返される場合にのみ恒久的な手順・記録を追加する。LEANと品質担保の優先順位に迷う場合は、独断で手続きを増やさずPOへ相談する。

## 未完了タスクの継続

- 検証・自己点検で未達を見つけた場合、外部判断待ち・必要な承認待ち・安全上の停止条件のいずれにも当たらなければ、handoffへの中間報告だけで作業を終了せず、そのまま是正と再検証を継続する。
- 完了回答を出す直前に、指示の完了条件を項目ごとに照合する。未達が一つでもあれば完了報告にしない。作業を継続不能な正当な理由がある場合だけ、未達項目・停止理由・再開時の最初の操作をhandoffに記録する。

## 指示境界の受領者チェック

MG・POからの指示を受け取ったら、着手前に次を確認する。

- 発信者・対象アクター・工程／目的が明確か
- 対象リポジトリ・対象パスが明確か
- 許可する操作・禁止する操作が明確か（特に編集・commit・push・公開の要否）
- 必須成果物・報告先が明確か

標準工程（100〜600の各`ad_app_*.md`）の既定スコープに収まる指示は、既定スコープの参照＋差分の簡略な指示で足りる。000_運用管理のように標準工程に当てはまらない指示、既定スコープを拡張・縮小する指示、PO直接指示は、上記4点をすべて明示的に確認する。

役割・対象・操作範囲・必須成果物のいずれかが不明・過大、または既存の`AGENTS.md`・このSkill・`WORKFLOW.md`と矛盾する場合、該当する編集・commit・push・公開操作を止める。疑義が指示の一部にしか及ばない場合はその部分だけを止め、他の部分は継続する。停止した場合も、読み取り・影響整理・分析・handoffへの報告は継続してよい（これら自体は取り消し困難な操作ではないため）。停止した項目・理由・安全な代替案・確認したいことをhandoffの完了報告（または中間報告）に記録し、MG（MGが機能しない場合はPO）へ確認する。

## 200_設計・400_テストにおける指示境界の注意点

- 200_設計で`DESIGN_LOG.md`がADのOUTPUTになる指示では、当該指示において`DESIGN_LOG.md`の編集とAD側でのcommit・pushを明示的に許可する。これは製品コード・`docs/internal-design/`・MG側の外部設計書の編集禁止とは別の扱いとする（`DESIGN_LOG.md`は500_リリース前作業で内部設計へ反映されるまでの作業用ログであり、要件定義書・外部設計書・内部設計書のいずれにも属さないプロセス／連絡用ファイルである）。指示にこの許可が明記されていない場合、「対象・範囲不明瞭」として上記の受領者チェックで扱い、編集前にMGへ確認する。
- 400_テスト(バグ修正)の指示は、調査のみを求めるものか、修正（ソース編集・commit・push）まで含むものかを指示境界で明示する。区別がない指示を受けた場合は、原因分析・対処案の提示までにとどめ、修正への着手前にMGへ確認する。
