# 400_テスト(バグ修正) — AD実施要領

工程定義表全体は `WORKFLOW.md` を参照。本ファイルは 400_テスト(バグ修正) 工程における AD（アプリ開発担当）自身の実施要領のみを扱う。

## INPUT

- MG からの調査依頼

## 手順

手順の正本は [ad_app_900_bugfix-flow.md](../ad_app_900_bugfix-flow.md) を参照する。本ファイルでは7ステップを重複記載せず、バグ修正結果のOUTPUTと差し戻し先判断の材料のみを定める。

## 差し戻し先判断の材料

MG が 100/200/300 いずれかへの差し戻しを判断する材料として、原因分析結果に以下を添える。

- 原因が要件の曖昧さに起因する → 100_要件定義 を提案
- 原因が事前調査段階（100内）での実装コスト・影響範囲の見積もり誤りに起因する → 100_要件定義 を提案（200_設計ではなく100内の事前調査へ差し戻す）
- 原因が設計判断の誤りに起因する → 200_設計 を提案
- 原因が実装ミスのみに起因する → 300_実装 を提案

複数の指摘に異なる差し戻し先が付いた場合、それらを1本のプロンプトにまとめるなら最も上流（番号の小さい方）に揃える。100が1件でも含まれるなら全体を100として扱う。この判定は、MGが指摘を1本のプロンプトにまとめて送った場合にのみ適用する。個別に分割して送った場合は、各指摘の差し戻し先をそのまま使う。

## OUTPUT

- 原因分析結果（差し戻し先の提案材料を含む）
- 対処案
- 修正済みコード
